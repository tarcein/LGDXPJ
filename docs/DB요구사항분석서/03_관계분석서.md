# E-R 관계 분석서

`01_요구사항정의서.md`의 문장에서 연관성을 나타내는 동사를 찾아 관계를 뽑고, 각 관계의 **매핑 카디널리티**(1:1, 1:N, N:N)와 **참여 특성**(필수/선택 참여)을 결정한 것이다. 시각화된 전체 ERD는 `../ERD/01_구현스키마_ERD.mmd`를 참고하면 된다. 이 문서는 그 다이어그램을 만들기 전 단계인 "관계를 문장에서 뽑아내는 분석" 과정을 보여준다.

## 1. 다대다(N:N) 관계 — 관계 테이블로 풀어낸 경우

예시로 주어진 "회원-상품-주문" 패턴과 정확히 같은 구조가 이 서비스에도 여러 번 나온다. 두 개체가 다대다로 얽힐 수 있는 지점마다, 그 관계 자체가 속성(상태·사유·메모 등)을 가지는 별도 테이블로 풀려 있다.

### R01. 가족 구성원 — 돌봄 항목 (담당 배정)

> 가족 구성원은 여러 돌봄 항목을 맡을 수 있고, 하나의 돌봄 항목도 (동시에 여러 후보에게 요청이 갔다가 그중 한 명으로 확정되는 과정에서) 여러 구성원과 관계를 맺을 수 있다. 구성원이 항목을 맡으면 그 배정에 대한 상태(제안/수락/거절/완료/취소), 배정 출처, 요청자, 요청·응답·완료 일시, 특이사항 메모 정보를 유지해야 한다.
>
> → 관계 = **care_assignment (돌봄 배정)**
> → 가족 구성원과 돌봄 항목 : 다대다(N:N) 관계
> → 가족 구성원은 관계에 선택 참여 (아직 아무것도 배정받지 않은 구성원이 있을 수 있음)
> → 돌봄 항목은 관계에 선택 참여 (아직 아무에게도 배정되지 않은 항목이 있을 수 있음)
> → 배정 관계의 속성 : 상태, 배정 출처, 요청자, 요청·응답·완료 일시, 특이사항 메모, 재알림 발송 일시

### R02. 가족 구성원 — 가족 구성원 (돌봄 인수인계)

> 담당자가 바뀔 때, 이전 담당 구성원은 다음 담당 구성원에게 인수인계를 넘길 수 있고, 한 구성원이 여러 번 넘기거나 받을 수도 있다. 인수인계 시 브리핑 내용, 상태(대기/확인됨), 확인 일시 정보를 유지해야 한다.
>
> → 관계 = **care_handoff (돌봄 인수인계)**
> → 가족 구성원(전달자)과 가족 구성원(수신자) : 다대다(N:N) 관계 (같은 개체끼리의 재귀적 관계)
> → 전달자는 관계에 선택 참여, 수신자는 관계에 필수 참여
> → 인수인계 관계의 속성 : 브리핑, 상태, 확인 일시. 그리고 이 인수인계는 항상 하나의 돌봄 배정(care_assignment)에 딸려서 발생한다.

### R03. 돌봄 배정 — 가족 구성원 (예외 상황의 대체 담당자)

> 하나의 배정에 문제가 생기면 대체 담당 구성원을 지정해 예외 상황을 만들 수 있고, 한 구성원이 여러 배정의 대체 담당자로 지정될 수 있다. 예외 상황에는 사유와 승인 상태 정보를 유지해야 한다.
>
> → 관계 = **care_exception (예외 상황)**
> → 돌봄 배정과 가족 구성원 : 다대다(N:N) 관계
> → 돌봄 배정은 관계에 선택 참여, 가족 구성원(대체 담당자)은 관계에 선택 참여
> → 예외 상황 관계의 속성 : 사유, 상태, 생성 일시

## 3. 다형성(polymorphic) 관계 — FK로 만들지 않은 경우

`notification.action_type` + `notification.action_id`는 "이 알림이 무엇에 대한 것인가"를 가리키는데, 그 대상이 배정(care_assignment)일 때도, 인수인계(care_handoff)일 때도, 예외(care_exception)일 때도 있다. 대상 테이블이 매번 달라지므로 하나의 외래키로 고정할 수 없어 **의도적으로 FK 제약을 걸지 않았다**. 참여 특성은 항상 선택(둘 다 NULL일 수 있음)이다.
