## 1. 지표 설계 목적

서비스의 고객 경험 목표와 LG의 경영 난제인 지속적인 디지털 고객 접점 확대를 다음 네 가지 가치로 정의하고, 실제 사용 기록으로 확인할 수 있는 BX·CX·DX 지표로 전환한다.

| 핵심 가치 | 고객 경험 목표 | 대표 측정 지표 |
|---|---|---|
| 조율 부담 감소 | 가족 누구도 돌봄 조율의 책임을 혼자 짊어지지 않는다 | 충돌 감지 후 재배정 완료 시간, AI 담당자 추천 채택률, 배정 요청 응답률 |
| 인계 부담 감소 | 담당자가 바뀌어도 아이의 돌봄 정보가 끊기지 않는다 | 돌봄 완료율, 인수인계 확인률 |
| 확인 부담 감소 | 사용자가 계속 앱을 확인하지 않아도 중요한 일을 놓치지 않는다 | 알림 확인률, AI 채널 활용 비율, 가전 알림 활성화율 |
| 지속 접점 확대 | 가전 알림이 일회성 설정에 그치지 않고 가족의 반복적인 디지털 접점으로 남는다 | ZIPPY 주간 재방문율, 가전 알림 월간 활성 가족방, 가전 알림 D+30 활성 유지율 |

퍼포먼스 트래커는 다음 심사 기준을 충족하도록 구성한다.

1. **지표 설계:** 고객 경험 목표마다 정의·산식·목표값을 둔다.
2. **측정 구현:** 서비스 데이터베이스와 이용 이벤트에서 지표를 실제 수집하고 API로 확인한다.

## 2. 전체 KPI 목록

### 2.1 BX Performance Tracker — 비즈니스 경험

| ID | 핵심 KPI | 정의 및 산식 | 베타 목표 | 실제 측정 수단 |

| BX-01 | 가족방 생성량 | 측정 기간에 새로 생성된 가족방 수 | 주간·월간 추이 상승 | `family_group.created_at` |
| BX-02 | 초대 링크당 참여 인원 | 초대 링크 누적 참여 인원 ÷ 생성된 초대 링크 수 | 링크당 1명 이상 | `family_invite_link.join_count` |
| BX-03 | 현재 Pro 전환율 | Pro 가족방 수 ÷ 전체 가족방 수 × 100 | 10% 이상 | `family_group.plan` |
| BX-04 | Paywall→Pro 시작 클릭률 | Pro 시작 버튼을 누른 가족방 수 ÷ Pro 안내를 본 가족방 수 × 100 | 25% 이상 | `pro_paywall_viewed`, `pro_cta_clicked` 이벤트 |
| BX-05 | Pro 시작→결제 전환율 | 결제를 완료한 가족방 수 ÷ Pro 시작 버튼을 누른 가족방 수 × 100 | 15% 이상 | 이용 이벤트 + `payment_transaction` |
| BX-06 | 한도 도달 후 24시간 내 결제 전환율 | 기능 한도 도달 후 24시간 이내 결제한 건수 ÷ 전체 한도 도달 건수 × 100 | 기능별 비교 후 상위 전환 요인 확인 | `feature_limit_reached` 이벤트 + 결제 승인 시각 |
| BX-07 | 기간 내 결제 매출 | 측정 기간에 승인 완료된 결제 금액 합계 | 월별 추이 상승 | `payment_transaction.status = DONE` |
| BX-08 | 현재 활성 구독 비중 | 활성 상태 구독 수 ÷ 전체 구독 수 × 100 | 90% 이상 | `family_subscription.status` |
| BX-S01 | 가족 구성원 수별 Pro 전환율 | 보호자 3명 이하/4명 이상 가족방의 Pro 전환율 비교 | 다인 가족 전환 효과 확인 | 가족 구성원 수와 `family_group.plan` 결합 집계 |

BX-01은 가족방 생성량을 직접 집계한다. BX-04~BX-06은 단순 결제 건수만 보는 대신 사용자가 어떤 기능과 화면을 거쳐 결제했는지 확인한다.

| ID | 핵심 KPI | 정의 및 산식 | 베타 목표 | 실제 측정 수단 |

| DX-06 | 돌봄 완료율 | 완료된 배정 수 ÷ 수락 또는 완료 상태 배정 수 × 100 | 90% 이상 | `care_assignment.status` |
| DX-07 | 구성원당 AI 질문 수 | 사용자가 보낸 AI 질문 수 ÷ 활성 구성원 수 | 월 3회 이상 | `assistant_message.role = user` |

DX-03은 조율 부담 감소의 대표 지표다. 일정 충돌이 실제로 감지된 시점과 새 담당자가 확정된 시점을 같은 돌봄 항목 ID로 연결해 계산한다.

CX-09~CX-11은 LG의 경영 난제인 지속적인 디지털 고객 접점 확대를 검증한다. ThinQ 안에 ZIPPY가 탑재된다는 서비스 전제에서는 CX-11을 일상 접점 형성 지표로 해석한다. 현재 구현에는 실제 LG ThinQ 계정·가전 API가 연결되어 있지 않으므로 `ThinQ 전체 MAU 증가율`로 확대 해석하지 않고, ZIPPY 재방문과 구현된 TV·음성 가전 알림 경험의 활성 규모·유지율로 한정한다.

## 4. 측정 구현

### 4.1 저장 구조

`performance_event` 테이블에 다음 항목을 저장한다.

| 항목 | 용도 |
|---|---|
| `event_name` | 어떤 행동 또는 시스템 처리가 발생했는지 구분 |
| `tracker` | BX·CX·DX 영역 구분 |
| `family_id`, `member_id` | 가족방·구성원 단위 집계 |
| `correlation_id` | 충돌 감지와 재배정처럼 전후 이벤트 연결 |
| `properties` | 화면, 상태, 건수 등 비식별 분석 속성 |
| `occurred_at` | 기간·리텐션·소요시간 계산 |

가족방이 삭제되면 해당 가족방의 퍼포먼스 이벤트도 함께 삭제된다.

### 4.2 수집 API

| API | 용도 |
|---|---|
| `POST /api/performance/events` | 프론트엔드 화면 방문·앱 진입·결제 퍼널 이벤트 기록 |
| `GET /api/performance/event-counts?days=30` | 기간 내 이벤트별 발생 건수 확인 |
| `GET /api/performance/summary?days=30` | 현재 가족방의 BX·CX·DX KPI 집계 |
| `GET /api/performance/summary?days=30&scope=service` | 개발자 모드에서 전체 서비스 KPI 집계 |

전체 서비스 지표는 개인 내용 없이 건수·비율·평균만 반환한다. `scope=service`는 개발자 모드에서만 사용할 수 있다.

### 4.3 확인 방법

1. 백엔드 서버를 실행한다.
2. `http://127.0.0.1:8000/docs`에서 `performance tracker` API 그룹을 연다.
3. 가족방 단위는 `/api/performance/summary?days=30`으로 확인한다.
4. 개발용 전체 집계는 백엔드 환경 변수 `LGDX_DEV_MODE=1`에서 `/api/performance/summary?days=30&scope=service`로 확인한다.
5. 집계 기간은 `days` 값을 1~365 사이로 바꿔 비교한다.

응답에는 각 KPI의 ID, 이름, 값, 단위, 분자, 분모, 목표, 원천 데이터가 함께 포함된다. 따라서 결과 숫자뿐 아니라 산식과 데이터 출처도 같은 화면에서 검증할 수 있다.

## 5. 지표 해석 기준

| 상황 | 해석 원칙 |
|---|---|
| 분모가 0인 비율 | 임의로 0% 처리하지 않고 `null`로 표시 |
| 리텐션 대상 기간 미도달 | 해당 사용자를 D+7·D+30 분모에서 제외 |
| 리텐션 관찰창 일부만 경과 | 7~13일 또는 30~36일 관찰창 전체가 끝날 때까지 분모에서 제외 |
| 반복 일정 일괄 등록 | 실제 생성된 일정 인스턴스 수를 등록량으로 집계 |
| 동일 알림 재조회 | 최초 읽음 처리 시에만 `notification_opened` 기록 |
| 결제 재호출 | 이미 처리된 주문은 중복 결제·중복 전환 이벤트에서 제외 |
| 개발자용 Pro 미리보기 | 실제 승인 결제가 아니므로 결제 매출과 결제 전환에서 제외 |

베타 목표값은 초기 가설이다. D+30 관찰창까지 포함해 최소 6주간 실제 데이터를 수집한 뒤 표본 수, 가족 구성, Free·Pro 이용 비중을 함께 보고 목표값을 조정한다.

### 6.1 구현 상태 점검

| 검증 항목 | 수집 지점 | 집계·확인 수단 | 상태 |
